# Codex 实施任务：有限天气观测下的卡车—无人机协同取件优化

## 0. 任务与交付要求

你是具备运筹优化、随机仿真和 Python 工程能力的研究开发工程师。请在当前仓库中**实际创建代码、运行测试、修复报错并执行示例**，不要只写方案或伪代码。

研究问题：在真实天气随时空变化且仅可通过预算有限、存在误差和延迟的区域观测逐渐获得信息时，一辆卡车携带一架无人机共同完成全部已知取件订单。联合决定何时观测哪片区域、卡车路线、哪些订单交给无人机、无人机在哪个卡车访问节点起飞与回收，以及何时滚动重规划。要求可对比主动观测的增益。

优先实现**正确、透明、可复现、可逐步扩展**的仿真，不必在第一版实现指数级复杂的精确多阶段随机 MILP。必须保证没有使用未来真实天气的“上帝视角”，路线和无人机时间同步、订单服务唯一且货物最终返回仓库。

最终交付：可运行项目、README、示例配置、单元测试、批量评估命令、结果 CSV、地图路线图、天气/观测/事件时序图、策略比较图、简洁的研究说明。若某项无法完成，明确标注原因与现有功能，不可只保留空函数。

## 1. 分阶段完成

### M1：确定性协同取件（首先保证能跑通）
- 生成二维坐标地图、仓库与客户、道路距离、时间窗、重量、基础速度与固定天气。
- 实现单卡车单无人机：卡车的完整访问序列、客户卡车/无人机唯一分配、单客户无人机架次 `a=(i,j,k)`、`i` 必须在卡车序列中早于 `k`、无人机与卡车时间同步、卡车在回收点等待、载重及电量、完整事件日志。
- 初始全部卡车取件解；实现车辆客户 relocate/2-opt、将卡车客户改为无人机客户、把无人机客户改回卡车、起降点调整等局部搜索操作。只接受满足全部硬约束的方案。
- 导出一张路线对照图，卡车实线、无人机虚线、起飞点/回收点/客户编号明确标识。
- `python -m tdw.cli run --config configs/base.yaml --policy prior --seed 42` 能完成一次仿真。

### M2：动态天气 + 主动观测
- 天气按区域、时间离散为 `calm/moderate/strong`，真实天气由环境产生但隐藏于策略。
- 策略保留每个区域的当前天气信念概率；实现马尔可夫预测、存在噪声的天气查询、查询费用、预算、并发限制和查询结果延迟。
- 添加 `truck_only`、`prior`（不查询，仅先验）、`random_query`、`entropy_query`、`voi_query`、`oracle`（只作为不公平的理想信息参考）策略。
- 查询结果未返回之前，策略不得使用该信息；后验只在查询结果到达后更新，旧观测需要随时间传播以体现过时。
- 基于当前信念，对候选无人机任务用天气场景采样评估飞行时间、能耗、强风风险，并施加样本近似机会约束。

### M3：滚动时域 + 批量评估
- 使用离散事件调度器或准确的分钟级状态推进，卡车正在道路上/无人机正在飞行中的既定动作不可通过重优化瞬间撤销或瞬移。
- 每 5 分钟、查询结果到达、卡车到站、无人机回收等事件可触发重规划；只执行当前可落实的部分，再迭代。
- 至少支持实验：观测预算、观测精度、反馈延迟、强风概率、风险阈值和客户数量敏感性分析。
- 采用固定真实天气/订单情景和共同随机数公平比较各策略，导出批量结果和配对差异的 95% bootstrap 置信区间。

## 2. 具体仿真实例与建议默认参数

所有数据为**合成示意参数**，不可宣称为真实运营测量值，可通过 YAML 调整。

- 地图：`8 km × 8 km`，单仓库 `(4,4)` km；客户数默认 `12`，敏感性 `8/15/25`；天气分区 `3×3`；最大仿真时长 `180 min`。
- 卡车：速度 `8 m/s`；道路距离为欧氏距离 `×1.30`（MVP 合成路网）；车辆服务时间 `2 min/客户`；容量 `60 kg`。
- 无人机：名义空速 `12 m/s`；容量 `2 kg`；电池 `100 Wh`，保留 `20%` 余量；架次单客户取件；每次卡车回收后可换成满电电池（先假设电池供应充足）；起飞准备 `1 min`，回收处理 `1 min`，无人机客户服务 `1 min`；最大风速门限 `9 m/s`。
- 客户包裹 `0.3–2.5 kg`，客户时间窗根据实例生成；拖延时间允许并按分钟惩罚；所有订单必须成功取件并随车返回仓库。
- 天气：三类风速 `2/6/11 m/s`；区域风向可以固定为可知的区域气候向量，真实风速等级隐藏，按每 5 分钟转移；初始状态概率 `[0.55,0.30,0.15]`；默认转移矩阵 `[[0.85,0.13,0.02],[0.14,0.75,0.11],[0.08,0.22,0.70]]`。
- 观测：单次费用 `2` 合成成本单位，结果延迟 `3 min`，观测状态分类正确概率 `0.85`（另两类各 `(1-0.85)/2`），总预算 `4` 次，最多 `1` 个并发查询，同一区域同一时刻不得重复提交相同未完成查询。
- 优化：每次规划抽样 `40` 个未来天气情景；机会约束安全检查另采样 `200` 次；滚动周期 `5 min`；飞行危险概率门限 `ε=0.10`，论文敏感性另测 `0.05/0.10/0.20`；局部搜索迭代次数 `300`；固定随机种子。
- 合成统一成本：卡车 `1.0/道路km`，无人机能耗 `0.02/Wh`，时间 `0.30/min`，订单超时 `2.0/min`，查询 `2.0/次`，任务失败/安全事件单独记录并可附加大额惩罚（例如 `200/次`）；这些是无量纲成本权重，不能称为真实人民币报价。

可以为简化 M1 先采用所有客户无紧时间窗，M2/M3 再启用时间窗和天气变化。

## 3. 数学模型与状态

订单集合 `C`、天气区域 `R`、节点 `V={o,d}∪C`，在代码中同一个仓库拆为起点 `o`、终点 `d`；允许将合规卡车停靠点作为起降点。`truck_route=[o,...,d]`，`sortie=(i,j,k)`；`i` 和 `k` 是卡车路线中两个严格按先后顺序访问的起降点，`j` 是不在卡车取件客户集合中的无人机客户。每个客户恰好由卡车或者无人机服务一次。

目标：最小化期望综合成本
`E[C] = cT*truck_km + cE*drone_Wh + cO*query_count + cH*completion_min + cLate*sum_late_min + cIncident*incident_count`。

核心硬约束：
1. 客户唯一服务，每个客户的货物最终在卡车上；从仓库出发最后返回。
2. 卡车路径连通，不可跳点或隐性子回路；一个客户只被卡车直接服务一次。
3. 每次无人机飞行只能服务一个客户，货物重量 `q_j <= QD`；起点/终点可起降且由卡车访问，起飞节点必须先于回收节点。
4. 取件航段必须分开计算：`i→j` 空载、`j→k` 携货；无人机回收时才把货物交给卡车；若假定不中途卸货，`sum(q_j)<=QT`。
5. 时间递推：`L_a >= A_i + h_launch`；卡车 `D_i >= L_a`；`C_j = L_a + flight(i,j) + serviceD_j`；`R_a >= C_j + flight(j,k)`；`D_k >= max(A_k,R_a) + h_recovery`。非无人机节点按卡车服务时间更新，且所有起飞/回收必须尊重已发生事件。
6. 同一架无人机的不同架次不重叠：下一次起飞在上次实际回收之后；起飞、飞行、回收等待不可瞬移。
7. 若无人机比卡车先到回收点，MVP **假设该地点允许安全降落并等待**；否则须计入悬停能耗。默认只生成允许降落的起降点。
8. 每架次电量小于等于 `battery_capacity*(1-reserve_fraction)`，并满足当前信念下的风况安全机会约束；规划不等于实际必然安全，真实天气异常时由执行模拟器触发中止和卡车接管，记录风险事件，不允许无成本跳过失败订单。
9. 客户最早取件时刻满足；迟于最晚时刻产生 `lateness=max(0,pickup_end-latest)` 费用。
10. 查询数量/成本预算、并发占用和延迟必须真实执行；不能提前看到未完成查询结果。

无人机简化动力模型：对每条飞行航段 `p→q`，定义单位方向向量 `e`，区域风向矢量 `w`，估算地速 `v_ground=max(3, v_air + dot(w,e)) m/s`；飞行时间 `distance_m / v_ground`。功率 `P=180 + 25*payload_kg + 0.8*||w||^2 (W)`，航段能耗 `P * time_s / 3600 (Wh)`。若航段跨越多个天气区域，按直线与网格交段长度分段积分；不要只取客户所在区。上述模型是合成近似代理模型，README 中注明用于算法验证而非经过实测标定的飞行动力学。

天气在一次架次内如何变化：M2 可假设起飞时的区域风场在本架次期间冻结；M3 可选实现航段随时间更新。必须在 README 明确标注采用何种假设，并让天气门限与耗能计算一致。

## 4. 天气生成、观测与后验更新

`WeatherEnvironment` 在每个试验 seed 下独立预生成 `(time,region)` 的真实天气轨迹，只允许 `Simulator` 的物理执行模块读取，普通策略不能直接得到这个数组。区域在 V2 先相互独立、每 5 分钟通过同一已知转移矩阵推进；V3 可加共享扰动构造空间相关天气。

`BeliefTracker` 按区域存储状态概率 `b_{r,t}(w)`：
- 无新观测：按天气状态转移矩阵从上次时刻预测；
- 时刻 `s` 查询并在 `s+δ` 取得带噪标签 `z` 时，先拿查询时刻已存的先验 `b_{r,s}` 做 `b_post_s(w) ∝ b_{r,s}(w)*P(z|w)`，再利用马尔可夫矩阵传播到当前时刻；
- 同一区域查询未完成时，MVP 禁止再次查询，避免乱序融合；
- 不允许把“查询结果”硬设为绝对真实（除非实验专门把准确率设为 `1.0`）。

`PolicyState` 只包含：当前时间、客户完成情况、卡车位置和路径承诺、无人机状态、各区域 belief、已到达的天气报告、待返回报告、剩余查询预算与已发生成本。未来真实风速不得出现在策略对象、优化器 API 或日志输入中。

## 5. VOI 主动天气查询（必须正确处理信息时序）

使用**净信息价值**作为决策依据。`J_no` 是当前 belief 下、不增加本次观测时执行最优可行调度的期望总成本：
`J_no = min_policy E_b[C(policy,W)]`。

对于区域 `r` 的一个候选查询，结果标签 `z` 的预测概率 `P(z|b)` 来自当前先验与观测噪声矩阵。查询结果需要在 `t+δ` 才可见；在此之前的动作对全部可能报告 `z` 必须一致。用若干小规模情景 rollout 计算：
`J_query(r)=c_obs(r)+sum_z P(z|b)*J_delayed_recourse(r,z)`，其中 `J_delayed_recourse` 包括查询期间的共同执行成本/进度及到达后的最优可行后续调度成本，不能在 t 时刻提前分支使用 z。

`NetVOI(r)=J_no-J_query(r)`，预算和并发可行时优先选择 `NetVOI(r)>0` 最大的区域；若全部非正，不查询。**注意查询费用已经包含在 J_query 中，不得再扣第二次。**

为了保证项目可在普通 CPU 上运行，M2 可以实现并明确标记为 `approx_voi`：限制候选观测区域为未来 30 分钟内可行无人机航线覆盖的区域；比较不查询的期望规划成本与三个可能查询标签对应的延迟后验重规划成本；前缀动作共同冻结，采用少量情景 rollouts 或明确计入延迟造成的等待成本。不得使用 `sum_w b(w)*min_a C(a,w)` 代替无观测情形的 `min_a sum_w b(w)*C(a,w)`，那是非法的完美信息解。

没有接入查询的 `prior` 策略只依靠预测分布进行风险约束，不得因未观测就自动禁止所有无人机航线，也不得假定风况确定。

## 6. 联合路径优化和滚动执行

不要预先固定卡车路线后仅决定哪个客户使用无人机。M1/M2 至少需要联合调整：
- 卡车客户访问顺序（relocate、swap、2-opt）；
- 客户分工（truck→drone、drone→truck）；
- 无人机架次 `(i,j,k)` 的起飞/回收位置；
- 起飞、回收时刻和等待时间。

一个建议的启发式：
1. 全客户卡车取件路线作为初始可行解（最近插入+2-opt）。
2. 尝试把适宜客户切换为无人机任务并枚举路线中位置先后正确的起降点。
3. 对每个候选解，执行无重叠架次、时间同步、电量、载重、时间窗和机会约束校验；一旦不可行即拒绝。
4. 根据从当前 belief 采样的一组固定共同天气场景，估计预期成本。随机场景应在**同次局部搜索的所有候选之间共享**，避免因重新抽样而把噪声误认为优化。
5. 做 `300` 次邻域搜索（贪心改进或可复现的模拟退火），输出最优找到的可行路线，不需要保证全局最优；记录求解耗时。
6. 结束时使用独立的安全场景对被选择架次估计危险概率 `P(wind>limit OR energy>available)`；默认要求其估计值不高于 `ε`。这只是样本近似机会约束，不可声称有有限样本概率保证。

滚动流程：每次只执行已经开始的边或无人机架次，若查询仍未返回则使用现有信息继续做可行操作。每次重优化的起点是真正的动态执行状态；正在行驶的卡车边、空中无人机以及不可改变的已提交回收点必须保留。天气观测可以和车辆行驶并行，除非物理上必须等待查询结果才能决定起飞。

## 7. 离散事件仿真接口

推荐事件至少包括：`TRUCK_DEPART, TRUCK_ARRIVE, DRONE_LAUNCH, DRONE_PICKUP, DRONE_LAND, DRONE_RECOVERED, QUERY_START, QUERY_RESULT, WEATHER_TICK, REPLAN, EPISODE_END`。

每条日志记录：`episode_seed, policy, event_time_min, event_type, node_id, drone_sortie_id, zone_id, truck_position, drone_status, observation_available, budget_left, cumulative_cost`。可额外记录真实天气**只在仿真器的审计日志/图表侧**，不得作为普通策略输入。

在执行时若实际大风超出允许界限：MVP 将出发前安全互锁视为物理动作的执行可行性检测（不把区域真实风速传给规划器），取消该架次、记录一次计划失败/安全事件，并把订单交回卡车重新规划；不发生危险强行起飞，更不能把未取到的货物标为已完成。README 需明确：观测预算针对远程区域天气查询，出发前基础安全互锁不等于免费的未来天气观测。

进阶版本可以加入途中强风触发备降/返航与失败惩罚；V1~V3 核心验收只要求安全执行、任务可恢复，禁止静默跳过任务。

## 8. 策略与对照组

统一使用相同订单、相同隐藏天气轨迹以及一致的评估协议：

1. `truck_only`：全部卡车取件、无无人机、无额外天气查询。
2. `prior`：卡车+无人机、只使用先验和天气状态转移、不做查询。
3. `random_query`：预算与 VOI 相同，随机从近期相关区域查询。
4. `entropy_query`：预算与 VOI 相同，优先观测当前信念熵较高且未来可能经过的区域。
5. `voi_query`：用含成本与延迟的净 VOI 主动查询。
6. `oracle`：可查看未来真实天气的乐观参考方案，必须明确标记为“不可实现的完美信息参考”，绝不算作公平策略；若只用启发式，不能声称其目标是严格数学下界。

必须避免先比较不同 seed 的策略。把环境 RNG、观测噪声 RNG 和优化器 RNG 分离；同一 `seed` 下每个策略有同一事先生成的真实天气和订单。观测噪声应通过固定键 `(seed,zone,query_slot)` 生成或缓存，防止不同策略查询顺序影响基础环境。

## 9. 批量实验矩阵和评价指标

主实验：`8, 15, 25` 个客户；天气查询预算 `0, 2, 4, 8`；每个条件至少 `30` 个独立天气/订单 seed，最终可加至 `100`。先用小规模 sanity 测试，不要在首次运行就跑完整矩阵。

敏感性分析：观测准确率 `0.70/0.85/0.95`，观测延迟 `0/3/8 min`，先验强风概率约 `0.10/0.25/0.40`（调整先验分布并保留归一化），风险阈值 `0.05/0.10/0.20`。至少画出一个二维热力图分析“预算×观测延迟”或“预算×准确率”对 VOI 策略的影响。

每次仿真输出：
- `total_cost, completion_time_min, truck_km, drone_km, drone_energy_Wh`
- `query_count, query_cost, query_wait_min, drone_sortie_count, truck_wait_min`
- `on_time_rate, total_lateness_min, incident_count, canceled_sortie_count`
- `tasks_completed, infeasible_flag, planning_cpu_sec, total_wall_sec`

输出按策略分组的均值、标准差、配对差异和 paired bootstrap 95% CI，`mean_change=(mean(VOI)-mean(prior))` 及相对比例。仅给均值不够；报告查询成本和完成时间的折中，不应只展示一个总体成本。

## 11. CLI 与验收命令

至少支持以下命令（在项目根目录安装 `pip install -e .` 或提供 `PYTHONPATH=src` 可执行方式）：

```bash
python -m tdw.cli run --config configs/base.yaml --policy prior --seed 42
python -m tdw.cli run --config configs/base.yaml --policy voi_query --seed 42
python -m tdw.cli compare --config configs/base.yaml --policies truck_only,prior,random_query,entropy_query,voi_query --seeds 0:9
python -m tdw.cli sweep --config configs/experiment.yaml --seeds 0:29
python -m pytest -q
```

测试关键情形：
- 客户数为 1、单个货物超过无人机载重、风速全部强风、查询预算 0、观测准确率 1、查询延迟超过任务时长、多个客户相同位置、时间窗无法满足、无人机回收点无法抵达、一次查询尚未返回时重复查询。
- **时间不倒流**、车辆/无人机不瞬移、已执行动作不可回滚、卡车与无人机不会互相等待而死锁、无重复/漏取件。
- **信息隔离断言**：改变某个未来真实天气事件但保持当前可观测历史完全不变，直到报告/物理可观测事件到达，策略在当下输出动作必须相同。
- **VOI 单元测试**：构造两天气、两行动小问题，检查 `min_a E[C(a,W)]` 和 `E[min_a C(a,W)]` 不被混淆；当两个观测标签都不改变最优行动且查询价格正时，VOI 必须不大于 0。
- **反直觉案例**：当观测很贵、延迟很长时 VOI 能拒绝查询，而不是总把预算用完。
- 固定 seed 重复运行应得到完全相同的实验指标（除墙钟时间外）。
